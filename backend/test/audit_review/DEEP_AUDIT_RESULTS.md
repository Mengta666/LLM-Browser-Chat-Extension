## 新增确认的代码缺陷

### F10：会话超过 200 条后，恢复接口丢掉最新消息

位置：`backend/storage/chat_store.py:173–184`、`backend/api/sessions.py:36–55`、`extension/sidepanel.js:1434–1443`。

真实 SQLite 存入编号消息，再通过实际会话 API 读取：

| 存储消息数 | API 返回数 | 返回的最后一条（从 0 编号） | 结果 |
| --- | --- | --- | --- |
| 20 | 20 | 19 | 对照通过 |
| 200 | 200 | 199 | 对照通过 |
| 201 | 200 | 199，而非 200 | 最新消息缺失 |
| 260 | 200 | 199，而非 259 | 最近 60 条缺失 |
| 520 | 200 | 199，而非 519 | 最近 320 条缺失 |

SQL 是时间正序加 `LIMIT 200`，实际取得最早 200 条，不是最近 200 条。接口也没有分页参数。

另一个对照：260 条消息、摘要覆盖前 254 条，API 却只返回前 200 条。前端按全局摘要游标执行 `messages.slice(254)`，未摘要尾部变成空数组，剩下 6 条近期消息全部无法用于恢复。20 条消息、摘要覆盖 14 条时正常。

这是读取/恢复时丢失上下文，**不是数据库中的消息被物理删除**。仅把 SQL 改成读取最近 200 条还不够，必须同时统一摘要游标与返回消息的索引范围。

用例：`test_history_latest_message_survives_reopen`、`test_summary_reopen_keeps_unsummarized_tail`。

### F11：删除文档不核验所属知识库，元数据与向量分裂

位置：`backend/api/kb.py:192–196`、`backend/rag/kb.py:160–169`、`backend/storage/kb_store.py:201–209`。

隔离环境中把文档及 3 个片段放在 KB A，再请求 `DELETE /v1/kb/B/docs/A的doc_id`：

- B 是另一个真实存在的测试库：HTTP 200，A 的文档元数据被软删除，A 的 3 个有效向量仍在，真实 `search_kb(A, ...)` 返回 3 条。
- B 是不存在的 KB ID：结果相同。
- 对照：文档状态查询使用不匹配的 KB ID，会正确返回 `not_found`，没有删除元数据。

原因是向量失效使用请求中的 `kb_id + doc_id`，SQLite 删除却只按 `doc_id`。应在任何修改前校验文档所属库，并让更新条件保持一致。

影响是跨库误操作及“列表中已删除、仍然可以检索”。本测试不证明跨用户越权，也不表示正常前端点击必然会拼出错误的库 ID。

用例：`test_cross_kb_delete_cannot_modify_other_doc`，两种错误父级。

### F12：知识库恢复遇到一次向量服务故障后，直接重试无法修复

位置：`backend/rag/kb.py:296–304`、`backend/storage/kb_store.py:255–282`。

先正常软删除隔离 KB。仅在实际 Qdrant client 的第一次恢复 `set_payload(valid=True)` 调用注入一次临时异常，后续调用允许正常执行：

1. 首次恢复返回 HTTP 500。
2. SQLite 的 KB 和文档已被标记为恢复，3 个片段却仍失效，有效片段数为 0。
3. 再次调用恢复返回 HTTP 400：`KB 不在回收站`。没有再次尝试向量恢复。

无故障时，删除→恢复后 3 个片段全部恢复，正常对照通过；单独删除过的文档也不会被错误级联恢复，对照通过。

影响是在暂时故障后出现“库和文档可见、检索为空”，且恢复接口不能直接重试收敛。不是永久数据丢失；需要可重试的恢复状态流程或补偿处理，不应把两个独立存储的更新视作同一事务。

用例：`test_restore_after_transient_vector_failure_can_retry`。

### F13：后续批次写入失败，失败文档的前一批片段仍可被检索

位置：`backend/rag/kb.py:80–84,91–132`、`backend/agent/memory/vector.py:280–318`。

实际上传 TXT，经真实后台线程、SQLite 和内存 Qdrant 处理；切片与嵌入边界使用确定性测试数据，保留真实批量写入和失败处理：

| 切片数与故障点 | 元数据状态 | 有效片段 | 结果 |
| --- | --- | --- | --- |
| 64，无故障 | indexed，64 片段 | 64 | 通过 |
| 65，无故障 | indexed，65 片段 | 65 | 通过，确实跨两批 |
| 65，第一批失败 | failed，0 片段 | 0 | 通过 |
| 65，第二批失败 | failed，0 片段 | **64** | 失败，真实 search_kb 仍返回 3 条 |

第一批 64 个点成功写入，第二批 1 个点抛异常。后台只更新 failed 状态，没有让已写片段失效；检索又不以文档的索引成功状态作为准入条件。

影响是问答可能引用一个界面标记为索引失败、内容只入库一部分的文档。应考虑索引完成后再发布有效片段，或在失败时清理/失效本次写入并支持重试。未在真实服务器上注入故障。

用例：`test_upload_batch_failure_leaves_no_active_partial_doc`，4 种批次对照。

### F14：日志查询未指定过滤条件时返回 500

位置：`backend/observability/logger.py:71–78`、`backend/api/logs.py:15–25`。

隔离 API 测试与当前运行中的真实后端结果一致：

| GET 请求 | HTTP 状态 |
| --- | --- |
| `/v1/logs/query?channel=kb&limit=1` | 500 |
| `/v1/logs/query?channel=kb&event=kb_search&limit=1` | 200 |

无 `session_id/level/event` 过滤时，`results` 仍然是 deque，`results[-limit:]` 不受支持；指定过滤条件后转成 list，才可以切片。

这是内存日志查询接口故障，不代表日志文件丢失。排障时临时带上 `event` 等过滤条件能绕开，但根因仍应修复。

用例：`test_log_query_works_without_event_filter`。

## 真实精排扩展评测

数据：`kb_171d1dfb`，4 份虚构设备文档、6 个实际存储的有效片段。模型：`qwen3-reranker-4b-awq-int4`，阈值 0.5，保留前 5。归档运行开始时间：2026-09-12 14:42:04 UTC。

直接读取这 6 个片段，将全部候选传给真实精排服务，再按配置过滤；**没有执行 embedding/混合召回或最终答案生成**。因此本实验能隔离精排与阈值的影响，不能评价大库召回率。

- 14 个有答案问题，每个两次：28 次中，26 次保留所有预期来源；2 次失败均为同一个跨文档问题。
- 2 个无答案问题，每个两次：4 次均无片段超过阈值。分别为不存在设备和已知设备但资料未提供的主控频率。
- 单次调用约 0.308–0.515 秒。两轮个别分数有小幅变化，全部保留/漏掉判定一致。
- 这里的通过条件是“必要来源被保留”，不是“所有候选都相关”或“最终回答正确”。

### 已证实：复合问题的一个必要来源会被过滤

问：`Atlas-R7 校准用什么标准块，送料轴承又是什么型号？`

| 文档 | 两轮精排分数 | 0.5 阈值后 |
| --- | --- | --- |
| 操作规程（提供标准块） | 0.996989 | 保留 |
| Boreal-T2 手册（另一型号） | 0.653974 | 保留 |
| 备件目录（提供所问轴承型号） | **0.092169** | **过滤** |

拆成两个完整问题的对照，两次结果均为：

- `Atlas-R7 校准用什么标准块？`：操作规程 0.999780。
- `Atlas-R7 送料轴承是什么型号？`：备件目录 0.998711。

因此不是“文件没有入库”，而是单条复合查询经精排及阈值处理后丢了必要材料。建议通用的多意图拆分与证据覆盖检查，不针对这一条问题写特例；本轮没有实现，也没有直接调整阈值。Agent 后续可能补查，不能推导为最终必然答错。

### 型号与语言对照：高分不是型号适用性的硬保证

英文问 Atlas-R7 的 E731 复位，Boreal-T2 手册为 0.949355，Atlas-R7 操作规程为 0.929815，两次都如此。两者都被保留。

注意：Boreal 文档本身包含 Atlas 的对照警告，因此“另一型号文档高分”并不等于完全无关；这里只说明不能把排名第一视为参数适用性的证明。本轮没有观察新的最终回答串型号事件。

另一个查询形态对照：电容容量与输送带厚度的完整问句，正确片段约 0.998；关键词形式约 0.506–0.507，虽然本轮仍通过，却非常接近阈值。是否降低阈值必须结合多组正负例，不能只为一次命中调参。

原始分数：[rerank_matrix_results.json](rerank_matrix_results.json)。可执行脚本：[live_rerank_matrix.py](live_rerank_matrix.py)。
